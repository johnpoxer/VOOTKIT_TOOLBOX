## Immediate (Critical)

### 1. Devanagari PDF support
Hindi, Marathi and Nepali are currently refused with an explanation rather than attempted, because `@pdf-lib/fontkit@1.1.1` either throws `regeneratorRuntime is not defined` while subsetting, or — without subsetting — freezes the renderer until the tab is killed. Reproduced twice in a live browser.

Approaches, in order of likely success:
1. Source Noto Sans Devanagari as **TTF** rather than fontsource WOFF — the failure may be in WOFF decompression rather than shaping.
2. Load `regenerator-runtime` before fontkit (partially tested; inconclusive because the renderer was already wedged).
3. Newer fontkit, or `pdfkit`'s bundled build.

Acceptance: `नमस्ते दुनिया` renders in a downloaded PDF, embed completes in <5 s, no renderer freeze. Then remove the entry from `UNSUPPORTED` in `tools-pdfmake.js` and add a browser smoke test.

### 2. Client-side error reporting
**Highest-leverage item in the audit.** Two tools were broken in production with no signal. Both would have surfaced within a day of shipping this.

Implement the protocol's `error_logs` table in Supabase (`id`, `tool_name`, `error_type`, `message`, `timestamp`, `severity`, `resolved_status`). Wire every tool's `catch` into it — the engines already funnel failures through a single error path per engine, so this is roughly three call sites, not 257.

## This sprint (High)

### 3. Real browser smoke tests in CI
The 907 existing assertions cover pure functions only. Both bugs fixed here were in the gap between "arguments are correct" and "the tool works."

Headless-browser test per engine: load the page, assert the workspace mounted, feed one representative input, assert real output. Prioritise the tools with heavy external dependencies — PDF, video, audio, OCR.

Include the inputs that actually broke things:
- Text to PDF: emoji, ₹, Chinese, Cyrillic
- Video: a VFR WebM from `MediaRecorder`, and a clip with no audio track

### 4. CDN integrity and liveness
Every heavy library and font comes from jsDelivr or unpkg with no SRI and no fallback.
- Add SRI hashes to fixed-version CDN `<script>` tags.
- CI check that every CDN URL in `assets/js/*.js` returns 200. `@fontsource@5.0.19` 404'd silently; the same class of failure would take out ffmpeg.
- Add a test asserting the ffmpeg worker chunk name (`814.ffmpeg.js`) still exists for the pinned version — the code comments already flag this coupling as fragile.

### 5. Self-hosted fallback for critical libraries
pdf-lib (~1 MB) and fontkit (~200 KB) are small enough to vendor. On CDN failure, fall back to a local copy rather than failing the tool. ffmpeg (~30 MB) stays CDN-only.

## Quality (Medium)

### 6. Normalise tool registration
`T`, `TOOLS`, `DOCS`, and a direct `data-tool` comparison are all in use. This defeated three successive versions of the auditor. Settle on one shape, migrate the four outliers, and assert it.

### 7. Trim 87 over-length titles
All 87 remaining LOW findings. Longest is 82 characters (`tools/business/amazon-fba-calculator`); Google truncates past ~60. `docs/tool-registry.json` lists each one.

### 8. Measure real wasm memory ceilings
The new 200 MB / 30 min / 4K guards are informed estimates, not measurements. Establish the actual failure point per tool and set limits from data.

## Polish (Low)

### 9. Granular progress
The protocol asks for "Processing page 4 of 10" rather than "Loading…". The video engine already reports fractional progress; PDF and image tools do not.

### 10. Tool health dashboard
`docs/tool-registry.json` is regenerated by `npm run audit` and already carries per-tool scores and issues. Render it at `/admin/tool-health` with the 🟢/🟡/🔴 banding, joined against `error_logs` from item 2 once that exists.
